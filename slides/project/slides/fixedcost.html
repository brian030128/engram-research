3.1 · FIXED PER-TOKEN LOOKUP COST

Why lookup cost stays flat as memory grows

rows read per token = (N − 1) × K per layer; V4.1: 3 × 8 = 24

When the table grows…What happens per token
Rows in the table: 2.6 × 10⁵ → 384MRows read stay the same
Hashing workUnchanged: a few integer multiplies and modulos
Data movedUnchanged: about 6.3 KB per layer in V4.1
Key/value projectionFixed cost; grows with width, not rows (~157M weights per V4.1 layer)

Caveat: O(1) is algorithmic. Bigger tables mean more cache and TLB misses, so real latency can still rise. Experiment C measures this.

Paper §3.1–3.2 and §6.4; V4.1 config. Byte and weight counts are our calculations.

The paper states communication volume scales with activated slots, not table size. The table can therefore grow from hundreds of thousands to hundreds of millions of rows without adding compute per token.
